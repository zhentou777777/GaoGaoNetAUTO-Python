## 逆向结论速览

### 全部接口一览

| # | 接口 | 域名 | 用途 | 需要凭据 |
|---|---|---|---|---|
| 1 | `GET /web/network/code` | 学校网关 | 取授权会话 + 二维码载荷 | 无 |
| 2 | `GET /api/network/auth?ip=<IP>` | 学校网关 | **免扫码认证主路径** | Bearer Token |
| 3 | `GET /api/network/auth?str=<UUID>` | 学校网关 | 网页扫码流程末跳 | Bearer Token |
| 4 | `GET /api/network/logout?token=&ip=<IP>` | 学校网关 | 下线某设备（归还名额） | Bearer Token |
| 5 | `POST /api/login` | 用户中心 | **账号密码换 Token** | 手机号 + 密码 |
| 6 | `GET /api/user` | 用户中心 | 用户信息（需 Token 验证） | Bearer Token |
| 7 | `GET /api/network/online` | 学校网关 | **在线设备列表** | Bearer Token |
| 8 | `GET /api/network/onestatus` | 学校网关 | 查询某 IP 是否在线 | Bearer Token |

> 第 7、8 两个接口是从**官方 APP 的 APK** 里逆向出来的（见下文「从 APK 逆向」）。

### 三条认证路径的关系

```
                  ┌─────────────────────────────────────┐
                  │   服务端唯一认定的身份凭证：          │
                  │   Authorization: Bearer <Token>     │
                  └─────────────────────────────────────┘
                                  ▲
              ┌───────────────────┼───────────────────┐
              │                   │                   │
      ┌───────┴────────┐ ┌────────┴─────────┐ ┌───────┴────────┐
      │ ① 账号密码登录  │ │ ② 扫码授权       │ │ ③ 抓包取 Token │
      │ POST /api/login │ │ 扫二维码           │ │ 手动复制        │
      └───────┬────────┘ └────────┬─────────┘ └───────┬────────┘
              │                   │                   │
              └───────────────────┴───────────────────┘
                                  │
                    拿到 Token 后，三者完全等价
                                  │
                  ┌───────────────┴───────────────┐
                  │  GET /api/network/auth?ip=IP  │  ← 只剩这一步
                  │  → 云高放行，本机上线           │
                  └───────────────────────────────┘
```

**核心认知**：`code` / `str` / 手机扫码，全都只是「一次性授权载体」。
服务端最终认的始终是 Bearer Token。所以只要手里有 Token，
后续每一次认证都能自己完成——**手机退化成一次性 Token 搬运工**。

### 关键实测数据

| 观测项 | 结果 |
|---|---|
| `/api/network/auth?ip=` 无 Token 返回 | `{"code":410,"msg":"登录状态已失效，您的账号可能在别处登录。"}` |
| 认证成功响应体 | `{"code":200,"msg":"认证成功。"}` = **36 字节** |
| Token 失效响应体 | 同上 code=410 = **81 字节** |
| Token 格式 | JWT，`eyJ0eXAiOiJK...`，长度 335 |
| `code` 会话有效期 | **10 分钟** |
| 每次请求 `/web/network/code` | 服务端下发**新的** `str` |

> 字节数这套判据在实际排查时非常有用：抓包列表里只看 Content-Length
> 就能判断那次认证成功没有，不用解密内容。

## 协议逆向全过程

### 起点：为什么原项目用不了

参考项目 [JasonYANG170/GaoGaoNetAUTO](https://github.com/JasonYANG170/GaoGaoNetAUTO)
（C++/Qt，GPL-2.0）逆向出了正确的接口语义，但有三个致命问题：

1. **仓库没有编译好的 exe** —— C++/Qt 源码，普通人跑不起来
2. **接入点参数硬编码成作者学校值**：`clientip=10.194.28.69`、`wlanacname=Panabit`
3. **必须手机 SSL 抓包**才能拿到 Token，门槛极高

本项目保持接口语义一致，但把硬编码全部改为**运行时探测**，并补齐了自愈能力。

### 第一步：确认接口可达性

```python
requests.get("http://hgs.auth.yungao-tech.com:1110/api/network/auth?ip=10.135.130.202")
# → {"code":410,"msg":"登录状态已失效，您的账号可能在别处登录。"}
```

这个 410 响应一次确认了三件事：
- 域名端口正确、服务可达
- 响应是 **JSON**（不是 HTML）
- **410 = Token 失效/未认证**（这是后面所有状态分类的锚点）

### 第二步：定位扫码页的真实结构

一个隐蔽的坑：**校外访问会被 301 到公网站点**。

```python
requests.get(".../web/network/code")                    # → 301 → apply.yungao-tech.cn
requests.get(".../web/network/code?code=", allow_redirects=False)
# → 301 → /web/network/code  +  Set-Cookie: str=<UUID>
```

必须带 `?code=` 参数（哪怕空值）才能拿到真正的页面。这直接决定了
`fetch_code_page()` 的实现方式。

### 第三步：破解二维码载荷

拿到页面后（4931 字节），内联 JS 里藏着二维码内容：

```js
var encoded = [253,172,255,253,166,255,175,168,179,252, ...];
var key    = 158;

var str = encoded.map(function (c) {
    return String.fromCharCode(c ^ key);
}).join('');
qrcode.makeCode(str);
```

**逐字符 XOR**，`key` 每个会话随机生成（实测见过 43、158 等值）。
解码结果是 UUID 形式，且**与 cookie `str` 完全一致**（已多次验证）。

```python
payload = "".join(chr(c ^ key) for c in encoded)
# → "d2c656d3-7a2d-424c-abb4-fd2ff4a596fe"  == cookie["str"]
```

> 这意味着**二维码可以纯本地渲染**，不必去扒服务端图片，也不必信任对方的图片端点。

### 第四步：寻找状态轮询接口（结论：不存在）

页面里**完全没有轮询 JS**。我逐个探测了所有合理候选：

```
/api/network/code?str=...     → 302
/api/network/status?str=...   → 302
/api/network/check?str=...    → 302
/api/network/str?str=...      → 302
/api/network/result?str=...   → 302
/api/network/query?str=...    → 302
/api/network/scan?str=...     → 302
/api/network/auth/status?str= → 302
/web/network/code/status?str= → 302
```

全部 302（校外未认证状态）。**没有轮询接口**这个结论本身很重要，
它直接推翻了"PC 靠轮询得知授权完成"的假设。

### 第五步：手机抓包确认末跳（决定性证据）

用户用 Moni Proxy 抓到 APP 流量，第一条即命中：

```
GET hgs.auth.yungao-tech.com:1110/api/network/auth?str=09df7bb3-9789-4ca5-a9d6-61eaf2305b6e
→ 200, Content-Length: 36
→ {"code":200,"msg":"认证成功。"}
```

**这就解释了整条链路**：手机 APP 扫的是 **PC 侧会话的 UUID**，
APP 用自己的 Token 调 `auth?str=<UUID>`，替这次会话完成绑定。

同时暴露了两个实现陷阱：

1. **`str` 每次请求都会变** —— 每次请求 `/web/network/code` 服务端都下发新的
   `str` cookie。所以「UUID 变了 = 二维码过期」是**错误逻辑**，会永远误判过期。
   正确判据是 10 分钟有效期计时。
2. 轮询时重拉页面会**覆盖 cookie 里的 `str`**，导致后续 `auth?str=` 用错会话标识。
   必须固定保存最初的 UUID。

### 第六步：逆向账号密码登录接口（彻底免抓包）

这是让「开机自启 + 断网自连」真正闭环的关键——**Token 必须能自己续**。

探测过程：

```python
# 1. 先确认方法
GET /api/login → 405 {"message":"The GET method is not supported for route api/login.
                       Supported methods: POST."}

# 2. 逐个试字段名（全都返回 400「参数不能为空」）
{"username":...} {"account":...} {"user":...} {"name":...}
{"loginName":...} {"phone":...} {"userId":...} {"studentId":...}
{"account":..., "pwd":...}

# 3. 命中
{"mobile": "138****8000", "password": "x"}
→ {"code":408,"msg":"手机号不合法"}     ← 字段被识别了！
```

> 文档里的手机号一律写成 `138****8000` 这种掩码形式 ——
> 文档会随安装包分发给很多人，完整号码可能被当成真实用户信息。

**最终接口**：

```
POST https://user.v4.yungao-tech.com/api/login
Content-Type: application/json

{"mobile": "<手机号>", "password": "<密码>"}
```

错误码语义（全部实测）：

| code | msg | 含义 |
|---|---|---|
| 400 | 参数不能为空 | 字段名不对 |
| 408 | 手机号不合法 | 手机号格式错 |
| 401 | 账号不存在 | 该手机号未在云高注册 |
| 401 | 密码错误 | 账号存在但密码错 |

> **关键认知**：云高账号体系里**手机号就是登录名**。
> 所以「用手机号 + 密码登录 → 拿 Token → 自动认证」这条路完全成立，
> 从此**不再需要抓包**。

### 第七步：确认 Token 消耗点

```
GET /api/user      （无 Token）→ {"code":410,"msg":"登录状态已失效..."}
GET /api/user/info （无 Token）→ {"code":411,"msg":"接口请求错误"}
```

只有精确路径需要 Token。`/api/user` 这个 410 也顺带验证了
「410 = Token 失效」这个判据可以推广到用户中心。

### 第八步：从官方 APK 逆向（决定性一击）

前面的结论都是靠"猜 + 试"。真正把服务端逻辑说清楚的是**官方 APP 本身**。

这个 APK 是 **uni-app（Vue）打包**的，逻辑是**明文 JavaScript**：

```
assets/apps/__UNI__A703B0A/www/
├── pageCampusNetwork/home.js     92 KB  ← 校园网络页面的全部逻辑
├── app-service.js               1.7 MB  ← 业务逻辑 + 接口路由表
└── app-view.js                  2.4 MB  ← 视图层模板
```

#### 提取出的完整接口路由表

```js
auth:          { url: "/api/network/auth",      type: "network"   }  // 用户上网认证
networkAuth:   { url: "/api/network/auth",      type: "network"   }  // 用户扫码认证
online:        { url: "/api/network/online",    type: "network"   }  // 在线设备列表 ★新
onestatus:     { url: "/api/network/onestatus", type: "network"   }  // 查询是否在线 ★新
networklogout: { url: "/api/network/logout",    type: "network"   }  // 设备下线
```

★ 标记的两个是**此前完全不知道的接口**，正是解决"不挤掉手机"的关键。

#### 设备类型 type 的含义

从 APP 的视图层模板里还原出 `type` 字段的语义：

| type | 界面文案 | 含义 |
|---|---|---|
| 1 | 手机 WIFI 使用中 | 手机通过 Wi-Fi 上网 |
| 2 | 电脑有线使用中 | 电脑通过网线上网 |
| 3 | 电脑 WIFI 使用中 | 电脑通过 Wi-Fi 上网 |

#### 单设备限制的真相

APP 里 `showSiglePopup`（Sigle = Single，单设备弹窗）的模板文案：

> **「该套餐已有设备使用，无法支持多台设备同时上网。」**
> 按钮：「查看当前设备」

这句话点明了两件事：

1. **限制来自套餐，不是技术封锁** —— APP 里还有套餐列表/转换订单接口
   （`api/order/getMyCombo`、`api/order/have`、`api/order/createConvert`），
   理论上可以升级到多设备套餐
2. 「查看当前设备」按钮 → 就是 `/api/network/online` 接口

同时 `type` 字段的出现说明服务端**能区分设备类型**，
但套餐限制依然按"同时只能一台"来判定。

#### 错误码语义（APP 里直接给出的）

```js
200 == o.code ? 成功
700 == o.code ? showNotice.open()      // 提示框
701 == o.code ? showSiglePopup.open()  // 单设备弹窗 ← "多台设备同时上网"
```

其中 `notice701` 会被存到本地存储，下次打开 APP 时弹一次——
说明 701 是服务端明确返回的"设备数超限"信号。

#### 实测服务端行为（关键）

拿真实 Token 逐个验证：

```
GET /api/network/online
→ {"code":200,"msg":"","data":[{"ip":"10.135.130.202","type":2}]}

GET /api/network/onestatus?ip=10.135.130.202
→ {"code":200,"msg":"当前设备在线"}

GET /api/network/auth?ip=<另一个IP>     （已有设备在线时）
→ {"code":409,"msg":"当前套餐只支持单设备认证，请检查在线设备"}
```

**三个关键结论：**

1. **服务端按出口 IP 记录在线设备**，与 MAC/设备类型无关地做互斥
2. **409 表示"已有设备在线"**，且**已在线的 IP 重复认证也返回 409**（幂等拒绝）
3. `onestatus` 是**按 IP 段**判断的——`10.135.130.x` 整段都返回"在线"，
   而 `1.2.3.4` 返回"不在线"。说明认证网关接管了整个网段

第 3 点很重要：它意味着**只要两台设备共用同一个出口 IP，
服务端就只看到"一台设备"**，从而不触发 409。

## 核心机制

### 1. 免扫码认证：为什么 `auth?ip=` 能跳过整环

| 接口 | 语义 | 凭据 |
|---|---|---|
| `GET /api/network/auth?str=<code>` | 授权「刚刚被手机同意的那次会话」 | Token + 已被授权的 code |
| `GET /api/network/auth?ip=<IP>` | **直接把指定 IP 挂进账号的在线设备** | **只要 Token** |

`code` 只是网页流程里传递「这次授权给哪台设备」的一次性载体。
走 `auth?ip=` 就把 code 整环跳过了。

### 2. 扫码授权的完整闭环

```
PC 拉页面 → 拿 str(UUID) → 本地 XOR 解码 → 本地渲染二维码
                                    ↓
                          手机糕糕 APP 扫描
                                    ↓
                 APP 调 GET /api/network/auth?str=<UUID>
                 （带 APP 自己的 Bearer Token）
                                    ↓
                    服务端把「该 session 对应的 IP」置为已上线
                                    ↓
                    PC 检测到本机已连通外网 → 完成
```

**为什么判定完成的信号是"本机能否上网"**：
既然服务端直接改写 IP 的上线状态，且页面无轮询接口，
那么唯一可靠的可观测信号就是**本机的实际连通性**。

```python
# netguard.probe_online() —— TCP connect，不发应用层流量
for host, port in [("223.5.5.5", 53), ("119.29.29.29", 53),
                   ("1.1.1.1", 443), ("114.114.114.114", 80)]:
    try:
        with socket.create_connection((host, port), timeout=1.2):
            return True
    except Exception:
        continue
```

### 3. 怎么做到"不挤掉手机，两台同时用"

这是用户实际最关心的需求。分析清楚后有**两个层面的解法**。

#### 先看服务端到底怎么判定的

实测数据：

| 场景 | 服务端响应 |
|---|---|
| 无设备在线，认证 A | `200 认证成功。` |
| A 已在线，认证 B | `409 当前套餐只支持单设备认证，请检查在线设备` |
| A 已在线，**再次认证 A** | `409`（同一条也拒绝，幂等） |
| 下线 A 后认证 A | `200 认证成功。` |

即：**服务端只认"当前有哪几个 IP 在线"，不区分是谁先来的**。
认证新 IP 会顶掉旧的（旧设备掉线），这是服务端行为，客户端无法绕开。

#### 解法一：共享出口 IP（推荐，无需任何特权）

关键观察：`onestatus` 是**按 IP 段**判断在线的
（`10.135.130.x` 整段返回"在线"，`1.2.3.4` 返回"不在线"），
说明**认证网关接管整个网段，服务端视角里"IP"就是唯一标识**。

于是：

```
手机连校园网 Wi-Fi  →  手机开热点  →  电脑连手机热点
                                          ↓
                        两台设备对外是同一个出口 IP
                                          ↓
                        服务端只看到"一台设备"（type=1 手机 WIFI）
                                          ↓
                              只需认证一次，两台同时可用
```

**程序如何配合**：认证前先查 `/api/network/online`，
如果本机出口 IP 已经在列表里 → **直接判定为"已在线"并跳过认证**。
绝不能执行 `logout`，否则会把共享中的连接断开、把手机踢下线。

这就是代码里的**共享模式**：

```python
# 0) 共享模式：本机出口 IP 已在服务端在线列表中 → 已经在线
devices = self.online_devices(token)
for d in devices:
    if str(d.get("ip", "")) == ip:
        return AuthResult(ok=True, status=OK,
                          message="本机出口 IP 已在服务端在线列表中",
                          stage="共享模式：检测到本机已在线")
```

#### 解法二：程序层面不再主动顶替

原来的行为是「认证失败 → 自动 logout 手机的 IP → 再认证」，
这**必然**会把手机挤下线。现在：

- `auto_kick_phone` **默认关闭**
- 认证失败时明确告诉你「被谁占着」，并给出两条可选路径
- 提供**「在线设备」窗口**：看得见谁在线（绿点=本机，黄点=其他设备），
  并能一键下线某台设备——把「谁让谁」的决定权交回给你

#### 解法三：升级到多设备套餐（如果学校提供）

APP 里有套餐相关接口：

```
GET  /api/order/getMyCombo      我的套餐列表
GET  /api/order/have             可转换套餐列表
POST /api/order/createConvert    生成转换订单
```

单设备弹窗的文案是「**该套餐**已有设备使用」——
既然按套餐限制，理论上升级套餐就能多设备。
（这些接口在云高用户中心的 `v3` 域名下，需要在校园网内访问。）

#### 三种解法的取舍

| 方案 | 前提 | 体验 |
|---|---|---|
| 共享出口 IP | 电脑连手机热点 | **最好**，两台同时在线，无冲突 |
| 不自动顶替 | 手动点「在线设备」切换 | 明确可控，不会莫名其妙掉线 |
| 升级套餐 | 学校提供多设备套餐 | 一次性解决，但可能要花钱 |

### 4. 单设备在线名额的互斥处理

云高账号同时只能有 1 台设备在线，这是**服务端硬限制**，无法绕开。
只能设计与之配合的行为：

```
auth?ip=<PC_IP>                        直接认证
  ↓ 失败
logout?ip=<PC_IP> → auth?ip=           清理本机陈旧会话后重试
  ↓ 仍失败（判定名额被占）
logout?ip=<手机IP> → auth?ip=          自动顶替手机
  ↓ 仍失败
明确报错：区分「Token 已失效」与「账号被其他设备占用」
```

配套设计：
- **「归还名额」按钮** —— 一键 `logout?ip=<PC_IP>`，把位置让回手机
- **只做 PC 独占** —— 不实现热点/ICS/路由器共享

### 5. MAC 随机化适配

单名额下 MAC 一变就被当成新设备，更容易撞限制。
本项目的做法是**完全不去管它**：

- 每次运行重新探测出口 IP 与 MAC（UDP connect 选路由 + `netprobe_win` 按 IP 精确配对物理地址）
- 出口 IP 变化时（守护线程检测到）立即重新认证
- 文档中提示用户可自行关闭 Windows 的「随机硬件地址」，但不强制

## 自愈架构

这是本项目与原版最大的差异。**光重放旧 Token 是不够的**——
Token 一旦被服务端轮换，重放会永远失败。必须能**自己换到新的**。

### 四层保障

| 层 | 触发条件 | 动作 | 用户成本 |
|---|---|---|---|
| **L0** | Token 失效 | `POST /api/login` 换新 Token → 重跑认证链 | **0** |
| **L1** | 认证响应下发新 Token | 解析并自动续存 | 0 |
| **L2** | 无 Token 且无账号 | 降级扫码模式 | 扫一下 |
| **L3** | 全部失败 | 提示重新抓包 | 走一次抓包 |

### 认证链的实现

```python
def login_chain_self_heal(self, ip, token, phone_ip, kick_phone, account):
    res = self.login_chain(ip, token, phone_ip, kick_phone)   # 四级链
    if res.ok:
        return res
    if res.status != TOKEN_INVALID:      # 只有 Token 失效才值得换
        return res
    mobile, password = account
    if not mobile or not password:
        res.message = "Token 已失效，且未配置账号密码 → 请在设置里填账号密码"
        return res

    lr = AccountLogin().login(mobile, password)
    if not lr.ok or not lr.token:
        res.message = f"Token 已失效，自动换 Token 失败：{lr.message}"
        return res

    res2 = self.login_chain(ip, lr.token, phone_ip, kick_phone)  # 用新 Token 重来
    if res2.ok:
        res2.stage = "Token 失效→自动换新 Token→认证成功"
        res2.new_token = lr.token      # ← 回传给上层存回本地
    return res2
```

### 断网重连：指数退避

```
NetGuard（发现层）          ReconnectLoop（重试层）
├─ 每 20s 探测外网          ├─ 15s → 30s → 60s → 120s（封顶）
├─ 连续 2 次失败才判断网      └─ 网络恢复即退出循环
├─ 检测出口 IP 变化
└─ 上报 offline 事件 → 启动重连循环
```

**为什么要有两层**：只探测一次就重试，遇到校园网长时间故障会失败；
只无限重试又可能打爆服务端。指数退避兼顾两者。

### 一个容易忽略的坑：认证成功 ≠ 外网通

校园网常见 DNS 未生效——认证接口返回成功，但外网仍不通。
所以认证成功后**实测一次连通性**，不通就如实提示并继续重试：

```python
time.sleep(1.0)
if probe_online():
    self.q.put(("status", ("online", "已认证在线", OK_C, f"IP {ip}")))
else:
    self.log("认证已通过，但外网暂时不通——可能是 DNS 未生效，稍后自动重试")
    self.q.put(("status", ("working", "已认证，外网未通", WARN_C, f"IP {ip}")))
    self.q.put(("call", lambda: self.guard.start_reconnect()))
```

### 几个值得说明的实现细节

**Token 加密存储**：以 Windows `MachineGuid` 为种子派生密钥，
SHA-256 计数器生成密钥流做流加密，再加 HMAC 完整性校验。

```python
seed    = machine_guid()                      # 机器指纹
enc_key = sha256(b"gaogao-token-enc|" + seed)
mac_key = sha256(b"gaogao-token-mac|" + seed)
cipher  = plaintext XOR keystream(enc_key)    # SHA-256 计数器流
tag     = hmac(mac_key, cipher)[:16]          # 完整性
blob    = "v1:" + base64(cipher + tag)
```

换机器/换用户读出来的密文**无法解密**（已实测验证）。

**图标零依赖生成**：`icons.py` 用纯 Python 手写 PNG chunk（zlib 压缩），
并把 PNG 塞进 ICO 容器 —— 不依赖 Pillow，打包体积更小。

**跨线程 UI 安全**：所有后台线程通过 `queue` 投递事件，
主线程 `_drain()` 统一消费。Tk 控件**只在主线程操作**。

```python
self.q.put(("call", self._open_qr))     # 后台线程要操作 Tk 时
# → _drain() 里执行 payload()，回到主线程
```

### 状态分类表

服务端响应统一归类到这几种状态，UI 据此给出不同提示：

| 状态 | 触发条件 | 处理 |
|---|---|---|
| `OK` | code=0/200 | 成功 |
| `TOKEN_INVALID` | **code=410** 或文案含"登录状态已失效" | 触发 L0 自愈 |
| `DEVICE_LIMIT` | 文案含"设备已满/重复登录"等 | 顶替手机 |
| `NOT_AUTH` | 被重定向 / 返回 HTML | 提示连校园网 |
| `HTTP_ERR` / `NETWORK_ERR` | 传输层失败 | 重试 |

> **`code:410` 的硬判断很关键**。早期版本只靠文案匹配，
> 而云高文案会变，导致自愈分支**从不触发**。改成按 code 判断后立刻生效。

## 实现取舍记录

### 为什么不做热点 / 路由器共享

云高单设备限制下，服务端只允许一台设备在线。
理论上 PC 做 NAT 共享给手机可以绕过，但：
- 需要管理员权限，配置复杂
- 违背学校的管理意图
- 本项目定位是「个人自用工具」，不做越权能力

### 为什么保留二维码兜底

账号密码路径（主）已经能完全免手机，但保留扫码有三个理由：
1. 账号是学号而非手机号时，账号密码路径不可用
2. 账号密码接口若被服务端改动，扫码是最后的兜底
3. 它是**唯一不依赖任何凭据**的路径

### 为什么需要 `capture.py`

虽然当前已逆向清楚主要接口，但云高是商业产品，接口可能变。
`capture.py` 用 Playwright 记录全部 XHR/fetch/Authorization 头/Cookie，
是**接口变更时的快速诊断工具**，也是给后来者的逆向起点。

## 复现这份逆向

想自己验证或适配其他学校？

```bash
# 1. 确认网关可达，看认证接口返回什么码
python -c "
import requests
r = requests.get('http://<你的网关>:1110/api/network/auth?ip=<你的IP>')
print(r.text)   # 期望看到 code:410
"

# 2. 登录接口探测（换你的域名）
python login_check.py <手机号> <密码>

# 3. 抓包分析（需要 Playwright）
pip install playwright && python -m playwright install chromium
python capture.py
```

**适配其他学校通常只需改两处**（设置界面里也能改）：
- 认证网关主机 / 端口
- `wlan_acname` / `paip` / `vlan` 接入点参数

其余逻辑（IP/MAC 探测、Token 自愈、重连退避）全部与学校无关。
